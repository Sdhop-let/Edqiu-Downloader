# 云盘同步技术调研报告

> 调研目的：为 XInvox（Edqiu / 小秋开发，安卓原生）的云同步功能设计提供技术方案输入。
> 聚焦范围：国内云盘为主（百度网盘、阿里云盘、腾讯微云、115、天翼云盘、和彩云、联通云盘），并补强 WebDAV / S3 / CloudDrive2 等通用通道。
> 技术深度：OAuth 授权、API 接入、增量同步、断点续传、冲突解决、去重。
> 调研时间：2026-08-15

## 1. 市面通用技术模式（跨产品提炼）

无论产品形态是"手机相册自动备份""网盘客户端"还是"NAS 同步工具"，底层同步机制都遵循同一套工程范式。理解这套范式，比逐个研究某家 API 更重要 —— 因为 XInvox 的 CloudBackup 模块本质上就是在实现一个**最小可用的同步引擎**。

### 1.1 授权：OAuth 2.0 的三种落地形态

| 形态 | 适用场景 | 代表产品 | 关键风险 |
|------|----------|----------|----------|
| 授权码 + PKCE(S256) | 有 WebView 的 App | 阿里云盘、Google Drive | 重定向 URI 劫持（需用 `app://` 私有 scheme 或 localhost） |
| 设备码轮询（Device Code） | 无浏览器环境 / 电视 / 桌面端 | 百度网盘、GitHub | 需轮询 `/token` 直到用户完成扫码；轮询间隔受 `interval` 限制 |
| WebView 截 token | 半公开 API（逆向） | 微云、115 逆向客户端 | 违反 ToS；token 可能随时失效 |

**思考点**：为什么百度用设备码、阿里用 PKCE？
- 百度的 PCS API 历史上为桌面端设计，设备码是其官方推荐流；
- 阿里云盘 Open API 面向移动 App，PKCE 是无后端（public client）最安全的流。
- **对 XInvox 的启示**：统一抽象 `AuthMode` 枚举，让每种云盘声明自己用哪种流，引擎层不关心细节。你的 `BackupTarget.authMode` 已经做对了这件事。

### 1.2 上传：分片 + 断点续传是标配

所有现代云盘都要求大文件分片上传（避免单请求超时、支持并发加速、支持断点）：

```
precreate / createFile  → 申请 uploadId / uploadToken
       ↓
uploadPart × N          → 并发上传分片（百度 4MB 固定；阿里 100KB~5GB 单片，≤10000 片）
       ↓
listUploadedParts       → 断网恢复时先查已传分片（续传兜底）
       ↓
completeFile            → 合并分片，服务端生成文件
```

**断点续传的核心**：本地必须持久化"已确认分片收据"（chunk receipt）。XInvox 的 `ChunkReceiptStore` 落盘到 `filesDir/backup_chunks/{taskId}.json` 正是这个角色 —— 这是业界标准做法，你的实现走在了正确轨道上。

### 1.3 去重 / 秒传：省流量的关键

用户重复备份同一文件（或云端已有相同文件）时，不应重新传字节：

| 云盘 | 秒传指纹 | 算法 |
|------|----------|------|
| 百度网盘 | `content-md5` + `slice-md5`（文件前 256KB 的 MD5） | MD5 |
| 阿里云盘 | `pre_hash`（前 1KB SHA1）→ `content_hash`（全文件 SHA1）+ `proof_code` | SHA1 + 私有 proof |

**启发**：秒传不是必须的，但能显著降低流量与耗时。XInvox 的 `AliPanTarget.supportsRapidUpload=true` 已接入阿里秒传；百度侧目前未接 `slice-md5`，是后续优化点（见路线图 P1）。

### 1.4 增量同步：本地账本为主，云端低频对账

"同步"不等于"每次全量扫描"。业界共识：

- **主数据源**：本地 SQLite 记录每个文件的 `path / size / mtime / local_hash / cloud_file_id / upload_state`。
- **云端对账**：周期性（如每天一次）调用 `list` API，用 `mtime` 或 `file_id` 做差异比对，仅上传新文件或变更文件。
- **百度** `listall` 支持 `mtime` 过滤；**阿里** 无 delta API，需自行 `listFiles` 拉全量后比对。

**XInvox 现状**：`BackupWorker` 用 `VIDEO_EXTS / IMAGE_EXTS` 白名单收集文件，但**缺少本地账本表**（无 `cloud_file_id` / `mtime` 记录），每次跑都是"重新收集 + 重新判断 exists"。这是 P1 的核心缺口。

### 1.5 冲突解决：语义必须统一

当本地与云端同名文件不一致时：

| 策略 | 行为 | 云盘支持 |
|------|------|----------|
| 同哈希跳过 | 哈希一致 → 不传 | 全部 |
| 重命名（auto_rename） | 云端已存在 → 加后缀 `_1` | 百度 `rtype`、阿里 `check_name_mode=auto_ignore` |
| 拒绝覆盖（refuse） | 已存在 → 报错 | 阿里 `check_name_mode=refuse` |

**一致性的重要性**：如果用户在不同设备备份，冲突语义不统一会导致"有的云盘覆盖、有的云盘重命名"。XInvox 需要一处集中定义冲突策略，而不是让每个 Target 各写各的。

### 1.6 频控与退避：被忽视的隐形杀手

| 云盘 | 频控特征 | 退避策略 |
|------|----------|----------|
| 百度 | `listall` ≤ 8–10 次/分钟（超频报 `31034`） | 指数退避 + 固定窗口限速 |
| 阿里 | HTTP 429 + `x-retry-after` 头 | 按头退避，最长数十秒 |

**XInvox 现状**：`HttpClient` 仅设超时与连接重试，**无频控 / 退避逻辑**。这是 P0/P1 之间最容易被忽视但最容易导致"备份跑一半卡死"的缺口。

## 2. 国内云盘可行性矩阵（2026-08 评估）

> 评分标准：⭐⭐⭐ 官方可用 / ⭐⭐ 受限可用 / ⭐ 仅逆向 / ❌ 不可行

| 云盘 | 官方 API | 个人开发者门槛 | 授权流 | 分片/续传 | 秒传 | XInvox 接入优先级 | 备注 |
|------|----------|----------------|--------|-----------|------|------------------|------|
| **天翼云盘** | ⭐⭐⭐ 官方开放 | 低（需注册应用） | OAuth 2.0 授权码 | ✅ | ✅ | **P0（补强）** | 国内唯一官方对个人相对友好的大厂盘 |
| **阿里云盘** | ⭐⭐ 暂停申请 | 2025-07 起暂停个人应用创建 | PKCE | ✅ | ✅ | 维持现状 | 已接入，但新用户无法授权 → 需引导文案 |
| **百度网盘** | ⭐⭐ 受限 | 上传权限需单独申请（报 `31024`） | 设备码 | ✅ | ✅ | 维持现状 + 引导 | 已接入，但上传权限可能被限 |
| **腾讯微云** | ⭐ 半公开 | 需商务合作 | WebView 截 token | 逆向 | 逆向 | 不优先 | ToS 风险高 |
| **115 网盘** | ⭐ 仅逆向 | 无官方 API | 逆向 | 逆向 | 逆向 | 不优先 | 稳定性差，易封号 |
| **和彩云（移动）** | ⭐ 仅逆向 | 无 | 逆向 | 逆向 | 逆向 | 不优先 | 逆向维护成本高 |
| **联通云盘** | ⭐ 仅逆向 | 无 | 逆向 | 逆向 | 逆向 | 不优先 | 同和彩云 |
| **WebDAV** | ⭐⭐⭐ 通用协议 | 无（用户自备服务器） | 无 / Basic Auth | ✅ | N/A | **P0（打磨）** | 最稳通道，NAS / 自建均可 |
| **CloudDrive2** | ⭐⭐⭐ 本机挂载 | 无 | AuthMode.NONE | ✅ | N/A | **P0（打磨）** | 已接入，本机 `127.0.0.1:19798/dav` 探测 |
| **S3 兼容** | ⭐⭐⭐ 通用协议 | 无（用户自备桶） | AccessKey | ✅ | N/A | **P0（新增）** | 对象存储最通用，建议补 |

### 2.1 关键结论

1. **官方最可行 = 天翼云盘**。它是国内大厂中唯一对个人开发者相对友好的官方开放 API。XInvox 当前 `ProviderRegistry` 未注册天翼，是明显缺口 → **P0 新增 `TianYiPanTarget`**。

2. **百度 / 阿里个人开发者受限**：
   - 阿里 2025-07 起暂停个人应用创建，已授权的老用户可用，新用户无法接入 → UI 需明确"暂仅支持已有授权用户"。
   - 百度上传权限需单独申请，报 `31024` 时要有引导文案。
   - 两者**维持现状 + 补限制引导**，不做架构改动。

3. **最稳通用通道 = WebDAV / CloudDrive2 / S3**：
   - 这三类不依赖任何云盘厂商的善意，用户自备服务器或挂载即可。
   - WebDAV 与 CloudDrive2 已接入，需打磨稳定性（退避、错误映射）。
   - S3 尚未接入，建议作为 P0 新增（对象存储协议最通用，兼容 MinIO / 阿里 OSS / 腾讯 COS / 七牛等）。

4. **逆向类（微云 / 115 / 和彩云 / 联通）不建议投入**：ToS 风险、封号风险、维护成本高，投入产出比低。

## 4. 对 XInvox 设计的原则性建议

在动手补代码前，先建立几条"不可妥协"的工程原则（这是 Socratic 引导的核心 —— 先想清楚 why，再写 how）：

1. **引擎与 Provider 解耦**：同步引擎（队列、状态机、账本、退避）不应知道具体是百度还是天翼。新增云盘 = 实现一个 `BackupTarget`，不动引擎。
2. **收据落盘先于字节传输**：任何分片上传前，先确保 `ChunkReceiptStore` 已写入。断电恢复时不依赖云端状态。
3. **频控是引擎职责，不是 Provider 职责**：退避逻辑放 `HttpClient` 或独立 `RateLimiter`，Provider 只声明"我有哪些频控特征"。
4. **冲突语义集中定义**：在 `BackupTarget` 或 `BackupEngine` 一处定义枚举（SKIP_IF_SAME_HASH / RENAME / REFUSE），各 Target 映射自身 API 参数。
5. **token 生命周期统一管理**：`CredentialStore` 应负责刷新调度（或至少暴露 `isExpired()` / `refresh()`），而非散落在各 Target 的 `ensureAccessToken()`。

这五条原则将直接指导路线图（下一文档）的 P0–P2 任务拆分。
